## 2. 功能详解

- **消费三个不同来源的事件**（本阶段消费面最重的组件）：`sales.order.created.v1`（生成应收凭证 + AR 台账 + 累加已用额度，超限发 `finance.credit.rejected.v1`）、`erp.inventory.adjusted.v1`（生成存货科目凭证，金额是占位换算 `abs(qty_delta)`，见设计计划 §9 第 8 条）、`mdm.customer.created.v1`/`.updated.v1`（维护 `customer_credit_snapshots` 摘要副本）。
- **幂等过账两层防护**：`command_idempotency`（claim-first，五个真正的写命令 `ClosePeriod`/`ReopenPeriod`/`LockPeriod`/`PostManualEntry`/`ReverseEntry`）+ `finance_journal_entries_source_uniq` 唯一约束（事件驱动的自动过账，防"两条不同消息指向同一张源单"）。
- **期间权威判定 + post_no 生成搭同一把锁**：`postEntryTx` 按业务日期锁住覆盖它的期间行（`FOR UPDATE`），期间不是 `OPEN` 就顺延到下一个 `OPEN` 的期间（设计计划 §3.1"迟到的凭证记进下一个开放期间"），同一把锁上再给 `post_no` 分配序号（`last_post_seq` 列 + `UPDATE ... RETURNING`，不用 `CREATE SEQUENCE`——序列在事务回滚时不退号，行内计数器会，见设计计划 §9 第 7 条）。
- **红字冲销**：`ReverseEntry` 产生一张借贷互换的新凭证，原凭证一个字不动；冲销凭证记入当前期间，不是原凭证的历史期间。
- **后台循环**（`module.go` 的 `Start`，三个并发跑）：Outbox 推送 + 周分区维护（`event_outbox`/`event_inbox`）+ 消费三个来源的事件。⚠️ 没有月/期间分区维护任务——`finance_journal_entry_lines` 的分区是迁移时随会计年度一次性建好的（设计计划 §9 第 6 条）。

## 3. 完整契约清单

**gRPC `erp.finance.v1.FinanceService`**（11 个 rpc，见 `contracts/erp/finance/v1/finance.proto`）：

| rpc | 类型 | 暴露到 REST？ |
|---|---|---|
| `CheckPeriodOpen` | 读，咨询性 | ❌ 组件间协议，权威判定在过账事务内部 |
| `ClosePeriod` / `ReopenPeriod` / `LockPeriod` | 写 | ✅ `/erp/finance/periods/{period}/{close,reopen,lock}` |
| `GetCreditExposure` | 读 | ✅ `/erp/finance/credit-exposure/{customer_id}` |
| `BatchGetCreditExposure` | 读 | ❌ 只给组件间 gRPC 客户端防 N+1 用 |
| `PostManualEntry` | 写 | ✅ `POST /erp/finance/entries` |
| `ReverseEntry` | 写，红字冲销不是删除 | ✅ `/erp/finance/entries/{id}/reverse` |
| `GetEntry` / `ListEntries` | 读 | ✅ `/erp/finance/entries[/{id}]` |
| `ListARLedger` | 读 | ✅ `/erp/finance/ar-ledger` |

**发布事件：** `finance.voucher.posted.v1`（旁路分析事件）、`finance.credit.rejected.v1`（核心交易事件，本阶段唯一一条"事件反向流回上游"的边，消费者是 `erp-sales`）。
**消费事件：** `sales.order.created.v1`（生成应收凭证+累加已用额度）、`erp.inventory.adjusted.v1`（生成存货科目凭证）、`mdm.customer.created.v1`/`.updated.v1`（维护客户摘要副本，含信用额度值）。

详细字段与判据见设计计划 `docs/design/erp-finance.md` §3、§4——那份是真相源，这里是速查表。

## 4. 数据模型

| 表 | 分区 | 唯一约束 / CHECK | 说明 |
|---|---|---|---|
| `fiscal_years` | 不分区 | `name` 唯一 | 会计年度，几行量级 |
| `accounting_periods` | 不分区 | `(period, legal_entity_id)` 唯一；`CHECK status IN ('OPEN','CLOSED','LOCKED')` | 期间三态，自然键是 `(period, legal_entity_id)` 不是数字 id。**一次性建好 FY2026 全年 12 个期间，不配后台自动建分区任务**（设计计划 §9 第 6 条） |
| `accounts` | 不分区 | `code` 唯一；`CHECK category IN (...)` | 科目表，迁移播种 5 个最小集（设计计划 §9 第 2 条） |
| `finance_journal_entries` | **不分区**（§2.3 幂等过账唯一约束要求） | `entry_no` 唯一；`post_no` 唯一（排除空串）；`(source_component, source_doc_type, source_doc_id, source_revision)` 唯一（排除 `source_component=''` 的人工凭证）；`CHECK status IN ('DRAFT','POSTED')`；`(period, legal_entity_id)` 外键指向 `accounting_periods` | 凭证头。两个单号分开：`entry_no` 创建时分配允许缺口，`post_no` 过账时分配 |
| `finance_journal_entry_lines` | `accounting_period` **LIST** 分区（不是 RANGE——期间是离散标识符，不是时间戳落在哪个区间） | `CHECK (debit>0 AND credit=0) OR (debit=0 AND credit>0)`（复式记账，一行恰好一边非零） | 分录明细，全系统唯一不按 `created_at` 分区的表。`accounting_period`/`legal_entity_id` 从头表冗余过来，避免每次数据权限过滤都要 JOIN |
| `ar_ledger` / `ap_ledger` | 不分区 | `CHECK amount>0`；`CHECK 0<=reconciled_amount<=amount`；`CHECK status IN ('OPEN','RECONCILED')` | 应收/应付台账，与总账分家（设计计划 §2.4）。`ap_ledger` 阶段二结构已建但暂无写入方（`erp-purchase` 是阶段六） |
| `customer_credit_exposure` | 不分区 | `CHECK exposure>=0` | 本组件自己算的"已用额度"物化值 |
| `customer_credit_snapshots` | 不分区 | `customer_id` 主键 | `mdm-customer` 的摘要副本，只有 `credit_limit`——与上一张表是两张表，更新时机不同（设计计划 §9 第 5 条） |

另有全组件通用的 `event_outbox`/`event_inbox`（周分区）+ `command_idempotency`（`ClosePeriod`/`ReopenPeriod`/`LockPeriod`/`PostManualEntry`/`ReverseEntry` 五个写命令共用一张幂等表）。

**实测验证**（Task 13，`erp_finance_test` schema 里真跑过）：同一张源单重投被 `finance_journal_entries_source_uniq` 拦下、两张人工凭证互不冲突、往不存在的期间建凭证被外键拦下、分录行一边为 0 一边非 0 才合法（两边都非零被 CHECK 拒绝）、分录行正确路由进 `finance_journal_entry_lines_2026_09` 分区、期间状态非法值被 CHECK 拒绝、up/down 迁移在空数据下可完整往返。

## 5. 开发

```bash
export TEST_PG_DSN="postgres://postgres:<密码>@localhost:5432/brickkit_db?sslmode=disable&search_path=erp_finance,erp_finance_archive"
export TEST_NATS_URL="nats://localhost:4222"   # 可选，缺省走 nats.DefaultURL
go test ./... -race -count=1
```

跑测试前必须先用真的迁移工具把 `erp_finance` schema 建出来（测试连的是真库，不是 mock）：

```bash
export DATABASE_USER=postgres DATABASE_PASSWORD=<密码> DATABASE_HOST=localhost DATABASE_PORT=5432 DATABASE_NAME=brickkit_db PG_SCHEMA=erp_finance
go run ./backend/cmd/migrate
```

**核心测试**是 `backend/internal/repo/repo_test.go` 的 `TestPostManualEntry_并发过账postNo连续无缺口`：15 个并发的手工凭证过账到同一个期间，断言 `post_no` 两两不同——去掉 `lockOpenPeriodForDate` 的 `FOR UPDATE` 手动验证过，这条测试会稳定报 `finance_journal_entries_post_no_uniq` 唯一约束冲突。**改期间锁那段代码后必须重跑这条测试**。

⚠️ 期间是有限资源（一年只固定 12 个），且测试连的是真实持久化的 schema——涉及期间状态推进（尤其是 `LockPeriod`，终态不可逆）的测试要写成"按当前状态继续推进"，不能假设每次都从 `OPEN` 开始，否则第二次 `go test` 就会失败（`TestClosePeriod_然后LockPeriod_然后不能反关账` 就踩过这个）。

## 6. 排障

| 症状 | 根因 | 修法 |
|---|---|---|
| 并发过账时报 `finance_journal_entries_post_no_uniq` 唯一约束冲突 | `lockOpenPeriodForDate` 没有 `FOR UPDATE`（或被误删），两个并发事务读到同一个 `last_post_seq` 值，各自 +1 后撞出重复的 `post_no` | 保留 `FOR UPDATE`：这把锁同时是设计计划 §3.1 要求的期间权威判定，也是 `post_no` 生成的序列化点，两个目的搭同一把锁，不要拆开 |
| 消费者测试里事件"发了但 handler 好像没跑" | `besdk.Consume` 的 `event_inbox` 按 `(subject, aggregate_id, version)` 做单调去重，这张表是持久化的——如果测试用固定的 `aggregate_id`（如 `"test-agg"`）+固定 `version`，第二次跑测试套件时这个组合已经"处理过"，`Consume` 会静默跳过，handler 根本不会被调用 | `aggregate_id` 必须用每次测试都不同的值（用被测实体自己的 id，如 `order_id`/`movement_id`/`customer_id`），不要用固定字符串。已在 `consumer_test.go` 踩过这条，同 `erp-inventory` 的既有约定 |
| 事件驱动的自动过账（`PostSalesOrderEntry`/`PostInventoryAdjustedEntry`）在"先插后捕获唯一约束冲突当重复"的写法下，第二次投递同一源单会让整个事务报错而不是安全跳过 | PostgreSQL 里一条语句真的执行失败后，整个事务被标记成 aborted，即使 Go 这层选择吞掉那个错误，事务在数据库那侧也回不去了，随后任何语句（含 COMMIT）都会失败 | 必须先 `SELECT` 判断源单是否已经处理过（`findExistingBySource`），确认没有才真的插入——见 `autoentry.go` 顶部注释 |
