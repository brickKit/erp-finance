# erp/finance 的设计

本页写这个组件为什么这样设计：术语、拥有的数据、状态、规则要点、命令与事件、依赖、实现状态与未决问题。写给要修改它的人与 AI。怎样使用、部署与配置在 `BRICKKIT.md`；代码在哪、怎样构建与测试在 `AGENTS.md`。

跨组件的规则在装配项目：会计事实契约、认领模式、应收形成、核销、付款认领、供应商票据与应付在协议 05，关账与迟到单据在协议 06，凭证号与金额在协议 14，期初在协议 16，审批在协议 09，数据范围在安全 07；决定 D47–D51。端到端的位置见装配项目的业务流程“订单到收款”“采购到付款”。首批范围是装配项目阶段计划 C4 的 P0 定的（AI 定，待复核；种子用一套通用演示科目表是维护者定的）。

## 边界

每个法人一个正式账簿（D51）：科目、凭证、应收应付未清项、核销、付款认领、供应商票据与匹配、会计期间；会计事实的契约与接收。

| 不在这里 | 归谁 |
| --- | --- |
| 账单与商业发票、出账额度 | `erp/billing`（本组件订阅它的“已出账”形成应收，D48） |
| 收付款单据、付款执行、银行对账 | `erp/payment`（按本组件定义的资金事实发布；付款前向本组件认领，D47） |
| 存货成本、暂估与调整 | `erp/costing`（按会计事实契约发布成本事实；订阅本组件的“票据单价确认”） |
| 信用额度与占用 | `erp/credit`（订阅本组件的应收事实） |
| 采购订单、收货与验收 | `erp/purchase`（本组件向它查询匹配依据，D50） |
| 税额的计算与校验 | `erp/tax`（远期）；本版票据上的税额由人录入（D49） |
| 审批的统一待办 | `infra/workflow`（C7）；本版在本组件里审批 |
| 伙伴、法人、币种本身 | `mdm/partner`、`mdm/org`、`mdm/currency` |

## 术语

| 业务叫法 | 定义 | 代码标识符 |
| --- | --- | --- |
| 科目、科目表 | 法人的会计科目；类别：资产、负债、权益、收入、费用；可记账的是末级科目 | `account`；`category`：`asset`、`liability`、`equity`、`income`、`expense` |
| 过账规则 | 一种业务事实怎样生成分录：规则键与各角色的借贷方向；来源不写科目 | `posting_rule`；规则键如 `sales_invoice`、`supplier_invoice`、`receipt`、`payment` |
| 科目映射 | 法人把“规则键 + 角色”映射到自己的科目 | `account_mapping`；角色如 `receivable`、`revenue`、`output_tax` |
| 凭证与分录 | 借贷平衡的一组分录；系统凭证由事实过出，手工凭证经审批 | `voucher`、`voucher_line` |
| 会计期间 | 法人按月的期间；过账日期决定期间 | `period`；状态 `open`、`closed`、`reopened` |
| 会计事实 | 来源按共享契约发布、由本组件按规则过账的增量事实 | 契约 `accounting_fact`；去重表 `fact_received` |
| 资金事实 | 收付款发布的到账、付款、退款、冲正，带认领清单；会计事实契约的一种 | 契约 `fund_fact` |
| 未清项 | 应收、应付、客户的贷方余额、人工未清项；记应结、已核销、认领中；没有单独的状态列：未清余额为零就是“已结清”，否则“未结清” | `open_item`；`kind`：`receivable`、`payable`、`credit_balance`；`amount`、`settled`、`pay_claimed` |
| 可用余额 | `amount − settled − pay_claimed`：核销、冲减与新认领只能用它（协议 05） | — |
| 付款认领 | 收付款付款前对一个未清项的认领（认领模式的付款用法） | `pay_claim`；状态 `pending`、`confirmed`、`formalized`、`expired`、`released` |
| 核销 | 资金与未清项在一个本地事务里的分配 | `allocation` |
| 供应商票据 | 供应商开来的票据：按采购订单匹配，或按费用登记；通过后形成应付 | `supplier_invoice`、`supplier_invoice_line` |
| 匹配 | 票据行与采购订单行的依据（`erp/purchase` 的 `MatchService.Basis`）比较，容差内通过 | `match` |
| 人工未清项 | 缺来源时由人登记的应收应付，经审批 | `kind` 同上，`origin` = `manual` |

| --- | --- | --- |

| `posting_rule`、`account_mapping` | 规则键与角色的方向；法人的映射 | 版本化 |
| `period` | 法人、年月、状态、期间修订 | 不删除 |

| `fact_received` | 收到的会计事实与资金事实的身份与内容摘要（去重，保留不短于账务保留期） | 随账务 |
| `open_item` | 未清项：法人、种类、伙伴、币种、应结、已核销、认领中、到期日、来源（账单、票据、人工）与单号 | 结清后保留 |
| `pay_claim` | 付款认领：认领身份、未清项、数量、状态、期限、正式化数量、冲回 | 随未清项 |

| `supplier_invoice`、`supplier_invoice_line` | 票据：法人、供应商、票据号、日期、币种、金额与税额、状态、登记人与差异批准；行：订单行或费用科目、数量、单价、匹配结果 | 不删除 |
| `invoiced_line`、`invoiced_movement` | 每个订单行已过账的开票数量（订单单位与基本单位），每条入库流水已开票的基本单位数量（SI02、SI03） | 不删除 |
| `finance_fact` | 本组件发布的增量事实（应收已形成、已核销、应收结清等），按身份读回 | 随账务 |

## 会计事实契约

本组件定义、来源组件发布（协议 05 的会计事实契约）。契约放在本组件的 `contract/` 里（`contract/events/shared/`），版本随本组件的契约标签；来源各发各的事件类型，在来源自己的流上：类型名是 `<来源的领域>.<来源>.accounting_fact.v1`（资金事实是 `…fund_fact.v1`），例如 `erp.costing.accounting_fact.v1`、`erp.payment.fund_fact.v1`，形状引用共享的 schema。本组件按装配清单订阅：配置键 `FINANCE_FACT_SOURCES` 列出“流 → 事件类型”，部署时按装了哪些来源填写，不逐个认识来源；来源上线不改本组件。

| 字段 | 说明 |
| --- | --- |
| `fact_id` | 来源在业务事务里生成；本组件按它与内容摘要去重 |
| `source` | 组件、单据类型、单据身份、单号 |
| `legal_entity_id`、`business_date`、`posting_date` | 过账日期通常等于业务日期；迟到时顺延（协议 06） |
| `rule_key` | 过账规则键；本组件按规则与法人的映射出分录 |
| `currency`、`exchange_rate` | 交易币种与汇率快照（法人本位币时没有） |
| `amounts` | 角色 → 金额（不带科目，来源不写科目） |
| `partner_id` | 可选；带了的形成或针对伙伴的未清项 |
| `dimensions` | 部门（`mdm/org` 的身份）等；首批只校验部门 |
| `service_period` | 可选的服务期间（递延以后） |

**资金事实**（`fund_fact`）是会计事实的一种，另带：种类（到账、付款、退款、冲正）、伙伴、公司账户、订单参考（带了的到账形成预收）、认领清单（认领身份 → 金额；只有付款与退款带，到账不带）、被冲正的资金事实身份。收付款（C3）按它发布；本组件按它核销。

**重复投递**：同一事实身份、同一内容摘要再来，本组件的收件表在同一本地事务里判重，不再过账、不再核销，回答成功（消息确认）；两次几乎同时处理时，第二个事务在收件表的唯一键上等第一个提交，然后判重。

## 状态

### 付款认领

认领的状态表照协议 05 的认领模式（付款用法：额度是未清项的可用余额，`claimed_total` 记在 `pay_claimed`；正式化就是核销），代码里是同一张表，单元测试逐格比较。

| 命令 | `none` | `pending` | `confirmed` | `formalized` | `expired` | `released` |
| --- | --- | --- | --- | --- | --- | --- |
| 认领 `claim` | 额度够时 → `pending` CL01 | 同一数量忽略，不同数量拒绝 CL02 | 同一数量忽略，不同数量拒绝 CL02 | 同一数量忽略，不同数量拒绝 CL02 | 拒绝 CL08 | 拒绝 CL08 |
| 续期 `renew` | 拒绝 CL03 | 未到期时允许 CL03 | 拒绝 CL03 | 拒绝 CL03 | 拒绝 CL08 | 拒绝 CL08 |
| 确认 `confirm` | 拒绝 CL03 | → `confirmed` CL04 | 忽略 CL04 | 忽略 CL04 | 拒绝 CL08 | 拒绝 CL08 |
| 到期 `expire` | 忽略 CL05 | → `expired` CL05 | 忽略 CL05 | 忽略 CL05 | 忽略 CL05 | 忽略 CL05 |
| 释放 `release` | 拒绝 CL03 | → `released` CL06 | 使用方发出时 → `released`，否则拒绝 CL06 | 拒绝 CL06 | 拒绝 CL08 | 忽略 CL08 |
| 正式化 `formalize` | 拒绝 CL03 | 拒绝 CL07 | → `formalized` CL07 | 同一数量忽略，不同数量拒绝 CL07 | 拒绝 CL08 | 拒绝 CL08 |
| 冲回 `reverse` | 拒绝 CL03 | 拒绝 CL09 | 拒绝 CL09 | 累计不超过正式化时允许 CL09 | 拒绝 CL08 | 拒绝 CL08 |

| 规则 | 内容 |
| --- | --- |
| CL01 | 认领按认领身份幂等；`pay_claimed + 本次 ≤ amount − settled`（可用余额），在锁住未清项的本地事务里裁决；期限起始 7 天 |
| CL02 | 同一认领身份再来：数量相同返回原认领，不同按冲突拒绝 |
| CL03 | 不认识的认领身份：认领以外的命令一律拒绝；续期只对未到期的待确认 |
| CL04 | 确认在收付款做出不可撤回的动作之前；确认后不再到期，只能由使用方释放或正式化 |
| CL05 | 待确认的认领到期由本组件的工作项执行，与确认在同一行上原子裁决；到期把认领中的数量退回可用余额。到期之后使用方要再付，用新的认领身份重新认领 |
| CL06 | 释放把认领中的数量退回可用余额；已确认的只能由使用方释放 |
| CL07 | 正式化在核销这笔资金的同一本地事务里完成（资金事实带认领身份）：按实付数量，剩余部分同时释放；不能先于确认。例：应付 1000，认领 600 已确认，付款事实带这个认领、实付 500：核销 500（`settled` 500），认领 `formalized`（500），剩下的 100 从 `pay_claimed` 退出、回到可用余额（应付的未清余额 500，可用余额 500） |
| CL08 | 已到期、已释放的认领：重复的释放返回成功，其余拒绝 |
| CL09 | 冲回（资金退回）按更正身份幂等，累计不超过正式化数量；同一事务里反向分配、未清项恢复 |

拒绝的原因：额度不足 `CLAIM_EXCEEDS_AVAILABLE`，同一身份不同数量 `CLAIM_CONFLICT`，状态不允许（含不认识的身份）`CLAIM_STATE`；系统面按 gRPC 的 `FailedPrecondition` 答，收付款据此不付。

### 供应商票据

一张票据要么全是订单行（订单票据，要匹配），要么全是费用行（费用票据，每行写费用科目，要批准）。

| 命令 | `draft` | `matched` | `mismatch` | `posted` | `cancelled` |
| --- | --- | --- | --- | --- | --- |
| 修改 `edit` | 允许 SI01 | → `draft` SI01 | → `draft` SI01 | 拒绝 SI05 | 拒绝 SI05 |
| 匹配 `match` | 订单票据允许，容差内变成 `matched`、否则 `mismatch` SI02 | 允许，重新匹配 SI02 | 允许，重新匹配 SI02 | 拒绝 SI05 | 拒绝 SI05 |
| 批准差异 `approve` | 费用票据允许 SI04 | 拒绝 SI04 | 允许 SI04 | 拒绝 SI05 | 拒绝 SI05 |
| 过账 `post` | 已批准的费用票据 → `posted` SI03 | → `posted` SI03 | 差异已批准时 → `posted` SI04 | 忽略 SI03 | 拒绝 SI05 |
| 取消 `cancel` | → `cancelled` SI05 | → `cancelled` SI05 | → `cancelled` SI05 | 拒绝 SI05 | 忽略 SI05 |

| 规则 | 内容 |
| --- | --- |
| SI01 | 登记与修改只在过账前，按版本整份替换行；改了回到 `draft`，清掉匹配结果与差异批准。供应商是活跃的伙伴；部门（可选）是法人的活跃部门；币种是法人的本位币（首批，外币票据随外币重估）；同一法人、同一供应商的供应商票据号不重复（已取消的除外，`CODE_TAKEN`）；内部号 `SI`（按法人与年，允许缺号）；行金额 = 数量 × 单价，按币种小数位舍入，税额由用户填（税组件以后） |
| SI02 | 匹配：在事务外向 `erp/purchase` 的 `MatchService.Basis` 取每个订单行的依据，按法人的匹配容差比较，每行写匹配结果（`ok` 或 `difference` 与原因）：订单行存在、法人与供应商与币种相同、订单已批准（`approved`、`completed`、`closed`）；数量按订单行的单位，不超过可开票数量 ×（1 + 数量容差%）：货物的可开票数量 = 已收（基本单位，净额）换算到订单单位 − 本组件已过账的开票数量，服务的 = 已验收数量 − 已过账的开票数量；单价与订单单价的差不超过订单单价 × 价格容差%。容差按法人声明（配置键 `MATCH_TOLERANCES`），起始都是 0。例：订单单价 100、已收 8，票据 10 件单价 105：数量超、单价超，进入 `mismatch`。没装 `erp/purchase` 时订单票据不能登记 |
| SI03 | 过账：一个事务里过出凭证（规则 `supplier_invoice`：订单行的不含税金额记 `purchase`，费用行记各自的费用科目，税额记 `input_tax`，价税合计记 `payable`；过账日期照 PD01 顺延）、形成应付未清项（伙伴是供应商，到期日按票据，部门照票据）、累计每个订单行已开票的数量；货物行按订单的入库流水先后分配基本单位数量（不超过每条流水的净收货减去已开票），每行发布一条“票据单价确认”（单价换算到每个基本单位，不含税）；服务行没有流水，不发布。过账前再取一次依据，依据变了（例如退货使可开票数量变小）就退回 `mismatch` |
| SI04 | 差异批准（`mismatch` 的订单票据、费用票据）：写明原因，批准人不是登记人（按账号；按自然人等 C7 的业务确认 profile），审计；批准后可过账 |
| SI05 | 过账后不能修改、不能取消；更正用供应商贷项（以后） |

### 手工凭证与期间

手工凭证（系统凭证由事实直接过出，状态就是 `posted`，不经这张表）：

| 命令 | `draft` | `submitted` | `posted` | `reversed` |
| --- | --- | --- | --- | --- |
| 修改 `edit` | 允许 VC01 | 拒绝 VC02 | 拒绝 VC04 | 拒绝 VC04 |
| 提交 `submit` | → `submitted` VC01 | 拒绝 VC02 | 拒绝 VC04 | 拒绝 VC04 |
| 批准 `approve` | 拒绝 VC02 | 审批人不是制单人时 → `posted` VC02 | 忽略 VC02 | 拒绝 VC04 |
| 驳回 `reject` | 拒绝 VC02 | → `draft` VC02 | 拒绝 VC02 | 拒绝 VC04 |
| 冲销 `reverse` | 拒绝 VC04 | 拒绝 VC04 | → `reversed` VC04 | 忽略 VC04 |

期间（首批没有关账批次，参与方还没有封存，关闭是本组件的本地动作）：

| 命令 | `open` | `closed` | `reopened` |
| --- | --- | --- | --- |
| 关闭 `close` | 没有待审批的手工凭证、之前的期间都已关闭时 → `closed` PD02 | 忽略 PD02 | 同左 → `closed` PD02 |
| 重开 `reopen` | 拒绝 PD02 | 写明原因 → `reopened` PD02 | 忽略 PD02 |
| 手工过账 `post_manual` | 允许 PD01 | 拒绝 PD01 | 允许 PD01 |

| 规则 | 内容 |
| --- | --- |
| VC01 | 每张凭证借贷平衡（本位币与交易币分别平衡）；只记可记账的启用科目 |
| VC02 | 手工凭证经审批，审批人不是制单人（按账号；按自然人等 C7），否则拒绝 `APPROVER_IS_SUBMITTER` |
| VC03 | 凭证号按法人与期间连续（协议 14 的连续序列），在过账的事务里取号；凭证不删除 |
| VC04 | 冲销凭证引用原凭证，金额相反，原凭证标为已冲销 |
| PD01 | 过账日期所在期间必须开放；来源的事实落在已关闭或重开的期间的，过账日期顺延到下一个开放期间的首日（业务日期不变，协议 06 的迟到单据；重开只为授权的更正）；手工凭证落在已关闭期间的拒绝 `PERIOD_CLOSED`（要计入原期间的，先重开）。期间在第一次过账到它时建立，状态 `open` |
| PD02 | 关闭期间：没有待审批的手工凭证、之前的期间都已关闭；重开要写明原因并审计；重开的期间只接受手工凭证（摘要必填、经审批），来源的事实照 PD01 顺延 |

## 应收、应付与核销

- **应收形成**（协议 05 第 2 步）：订阅 `erp/billing` 的 `erp.invoice.issued.v1`（“已出账”）：收到时按事实身份去重并排过账工作项，工作项在一个本地事务里形成应收未清项、过出凭证（规则 `sales_invoice`），发布“应收已形成”（下表 AR01–AR04）。账单的贷项（以后）冲减应收、不够的形成贷方余额。
- **核销**（协议 05 的核销）：资金事实到达时，一个本地事务里按身份升序锁住所涉未清项与资金行，分配不超过两者的较小值；带认领身份的用该认领占着的金额并正式化认领，不带的只用可用余额；没有指定未清项的到账按伙伴的最早到期应收自动分配，分不完的保留为未分配（预收与暂挂）；写分配、更新余额、过账（规则 `receipt`、`payment`），发布“已核销”与“应收结清”（应收的未清余额为零时）。冲正先于原事实到达时暂存，原事实到达后在同一事务中先核销、再冲回。
| 规则 | 内容 |
| --- | --- |
| AR01 | 一张已出账形成一个应收未清项（伙伴是客户，金额是价税合计）与一张系统凭证（规则 `sales_invoice`：应收 = 价税合计，收入 = 不含税金额，销项税 = 税额；凭证不经审批，审计的操作者是来源组件），发布“应收已形成”；到期日取账单带的到期日，账单没带时取开票日期；部门留空（账单不带部门） |
| AR02 | 同一事实身份、同一内容摘要只入账一次；同一身份、摘要不同：保留先到的、告警（日志事件 `fact_digest_mismatch`），不入账 |
| AR03 | 收件与过账分两段：收到事件的事务里只写收件表 `fact_received` 与一个过账工作项；工作项先在事务外取证（法人的本位币与代码、币种小数位），再在一个事务里过账、形成未清项、发布事实、把收件标为已过账。法人没有映射这条规则时，工作项等着（不耗尝试次数，间隔翻倍到 5 分钟），补上映射后最迟 5 分钟内过账；事实不丢 |
| AR04 | 本位币金额 = 交易币金额 × 事实带的汇率快照，按本位币小数位逐行舍入；舍入差调整到本位币金额最大的一行（同额取第一行），让本位币也平衡 |

- **人工未清项**：缺来源时登记应收或应付，经审批，过账规则 `manual_receivable`、`manual_payable`。

## 规则要点

- 金额：交易币与本位币都记；本位币金额 = 交易币 × 事实带的汇率快照，按本位币的小数位舍入（协议 14）；不在过账或核销时临时取汇率。币种不同的核销首批拒绝（外币重估与汇兑差额以后）。
- 单号：凭证 `JV`（连续，按法人与期间）；供应商票据的内部号 `SI`、人工未清项 `MI`（允许缺号，按法人与年）。
- 事实去重：同一事实身份、同一内容摘要只入账一次；摘要不同按“旧事实丢失、新事实到达”处理并告警（协议 05 的共同规则）。
- 审计：手工凭证的提交、审批、冲销，期间的关闭与重开，人工未清项，票据的过账与差异批准，认领的每次变化（协议 03）。

## 事件

流 `erp.finance`：

- 增量事实（不可遗漏，协议 05 的共同规则，按身份读回）：凭证已过账（首批没有订阅方，给以后的报表与预算）、应收已形成、已核销、应收结清、应收减少、应收重开（信用订阅）、票据单价确认与它的冲回（成本订阅）。
- 完整状态事件：期间状态。
- 订阅：`erp/billing` 的已出账；装配清单里的会计事实与资金事实（首批：收付款、成本以后才有，接收与核销先用替身测）。

## 未决问题

- 匹配容差按法人声明（SI02，AI 定，待复核）：契约里没有维护容差的接口，首批用配置键 `MATCH_TOLERANCES`（JSON：法人身份 → 数量与价格的容差百分比），没写的法人是 0；以后有财务政策的维护界面时搬过去。
- 供应商票据首批只收法人本位币（SI01，AI 定，待复核）：票据的契约没有汇率快照，外币票据随外币重估与汇兑差额一起做。
- 一张票据只有一种行（SI01，AI 定，待复核）：订单行与费用行混在一起时，费用行不经匹配也不经批准就会过账；分开后各自的检查都在。
- 应收的到期日（AR01，AI 定，待复核）：协议 05 的“已出账”不带到期日，伙伴角色的付款条件只是不透明的代码；首批取账单带的 `due_date`（出账契约以后加上时直接生效），没有就取开票日期。付款条件的含义与计算放在出账还是财务，到催款或付款建议真用到时再定。
- 摘要不同的同一事实（AR02，AI 定，待复核）：协议 05 要求按“旧事实丢失、新事实到达”处理（冲回旧的效果、按新的入账），只在来源整套恢复后才会出现；首批只保留先到的并告警，随整套恢复演练（协议 15）补上冲回。
- 共享契约的发布：来源组件在自己的契约里引用本组件契约的 schema（复制、按版本核对），还是本组件另出一个只有契约的仓库：首批放在本组件契约的 `contract/events/shared/`，来源复制并在测试里按版本核对，第一个来源（C3）开工时再看要不要拆出去。
- 币种不同的核销、汇兑差额：随外币重估一起做。
- 演示科目表只为演示，不代表任何国家的准则；上线时由当地会计换掉。
